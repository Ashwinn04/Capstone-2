1) Project Overview

Project Name

Sepsis Digital Twin — Deep Learning, Explainability, and Clinical Dashboard

Elevator Pitch

A production-style clinical AI that predicts sepsis risk 4–6 hours before onset, explains why, and presents actionable guidance to clinicians via a real-time dashboard and a REST API.

It integrates deep learning and classical models, evaluation metrics, and explainability into a cohesive, demo-ready system.

Tech Stack

  • Languages: Python 3.11 (Dockerfile), Python 3.8+ compatible
  • Backend: FastAPI, Uvicorn
  • Frontend: Streamlit (interactive dashboard)
  • ML/DL: PyTorch, scikit-learn, NumPy, pandas
  • Explainability: SHAP, LIME, Captum
  • Visualization: Plotly, Matplotlib, Seaborn
  • Packaging/Infra: Docker, Docker Compose

Purpose and Key Features

  • Early sepsis risk prediction (4–6h horizon) with ensemble of 7 models
  • Interactive Streamlit dashboard with 9+ tabs, dynamic explainability, and export tools
  • FastAPI microservice with endpoints for prediction, batch, explainability, health, and model status
  • Rich evaluation and clinical scoring (SIRS, qSOFA, SOFA), plus lead-time and timeliness metrics
  • Dockerized deployment paths: API-only, dashboard-only, or complete system
Results — Model Performance (Real Dataset)

Validation (patient-wise split, ensemble of 3 seeds)

  • GRU-D: AUPRC 0.2079, AUROC 0.5537
  • LSTM: AUPRC 0.1371, AUROC 0.5424
  • CNN_LSTM: AUPRC 0.1883, AUROC 0.5487
  • Transformer: AUPRC 0.1471, AUROC 0.5263

Test (calibrated, ensemble of 3 seeds)

  • GRU-D: AUPRC 0.1355, AUROC 0.4970, Brier 0.1114
  • LSTM: AUPRC 0.1353, AUROC 0.5430, Brier 0.1112
  • CNN_LSTM: AUPRC 0.1342, AUROC 0.5412, Brier 0.1111
  • Transformer: AUPRC 0.1423, AUROC 0.5382, Brier 0.1112

Note: Dataset positive rate ≈ 2.17%. Prefer AUPRC/AUROC over raw accuracy under imbalance. Reported results include probability calibration and thresholding at Recall≈0.85.

Model Quality Assessment

Overall Assessment: Modest performance. Test AUPRC ≈ 0.13–0.14 and AUROC ≈ 0.50–0.54 indicate weak discrimination above random chance, but better than baseline (AUPRC ≈ 0.02 for random classifier). Calibration is good (Brier ≈ 0.11), suggesting probabilities are reliable; the bottleneck is discrimination (ranking/separation), not calibration.

Key Findings:

  • Calibration: Excellent (Brier scores ~0.11 across all models). Probabilities are well-calibrated, meaning predicted probabilities match observed frequencies.
  • Discrimination: Limited. AUPRC ~0.13–0.14 is low but expected given the severe class imbalance (2.17% positive rate). AUROC ~0.50–0.54 indicates minimal separation between positive and negative cases.
  • Model Comparison: Transformer shows slightly better AUPRC (0.1423), while LSTM achieves the best AUROC (0.5430). GRU-D shows the largest drop from validation to test (AUPRC: 0.2079 → 0.1355), suggesting potential overfitting.
  • Thresholding: At Recall≈0.85, all models achieve similar precision (~0.12–0.13), indicating limited utility for clinical decision-making at this operating point.

Recommendations for Improvement

Priority 1: Data & Windowing

  • Increase positive sample density by sampling multiple windows per positive patient and fewer per negative patient.
  • Experiment with window lengths (24h vs 48h) and step sizes (2–3h vs 6h) to capture temporal patterns more effectively.
  • Use balanced or moderately imbalanced minibatches during training.

Priority 2: Loss Function & Class Imbalance

  • Sweep pos_weight values (e.g., 5–30) for BCEWithLogitsLoss to better handle the 2.17% positive rate.
  • Experiment with Focal Loss parameters: α ∈ [0.1–0.5], γ ∈ [1–3] to focus learning on hard examples.

Priority 3: Hyperparameter Tuning

  • Learning rate: Try 5e-4, 1e-3 (current), 2e-3.
  • Weight decay: Test 1e-5, 1e-4, 5e-4.
  • Dropout: GRU-D/LSTM/CNN-LSTM: 0.2–0.5; Transformer: 0.1–0.3.
  • Gradient clipping: 0.5–1.0 (currently 1.0).

Priority 4: Architecture Enhancements

  • GRU-D: Try hidden_size=256, ensure decay mechanisms use stable feature means per feature.
  • LSTM: Add layer normalization between layers, try hidden_size=256 or 3 layers.
  • CNN-LSTM: Add a third conv block (128→256) or larger kernels (k=5) to capture slower trends.
  • Transformer: Add learned CLS token for pooling, try nhead=4, layers=2–3 for smaller models.

Priority 5: Feature Engineering

  • Add first-order deltas and rolling statistics (mean, slope) for key features (HR, Temp, WBC, Lactate) over 6h windows.
  • Include observation frequency/mask ratios as features (missingness patterns).

Priority 6: Ensembling

  • Weight ensemble by validation AUPRC instead of uniform averaging.
  • Consider snapshot ensemble: average last 5–10 checkpoints around the best epoch for each seed.

Note: Simply training more epochs is unlikely to improve performance significantly, as early stopping and learning rate scheduling are already in place. Focus on data quality, feature engineering, and hyperparameter tuning instead.

Common Troubleshooting

  • Dataset missing: Dataset.csv required by dashboard; demo still runs with sample data but fewer features.
  • Ports busy: Change to -p 8001:8000 or -p 8502:8501.
  • SHAP/Captum heavy: Some environments need extra build tools; Docker image installs build-essential.
  • Mac ARM + Torch (MPS): Apple Silicon MPS has limitations. The codebase includes fixes for:
    • Float64 → Float32: MPS doesn't support float64. All tensors are explicitly cast to float32 (pos_weight, logits, targets, etc.).
    • Transformer padding mask: Nested tensor ops are unsupported. The Transformer model uses manual masked pooling instead of src_key_padding_mask.
    • Mixed precision: AMP/GradScaler is disabled for MPS (only enabled for CUDA). MPS uses standard FP32.
    • Fallback option: If issues persist, set PYTORCH_ENABLE_MPS_FALLBACK=1 to fall back to CPU for unsupported ops (slower but more compatible).
  • Absolute paths: Backend/dashboard add an absolute project_root; see Known Issues for the fix.

Components

  • Frontend: Streamlit app (`dashboard_real.py`) renders risk, explanations, trajectories, fairness, and exports.
  • Backend: FastAPI app (`api_service.py`) offers endpoints for predictions, explanations, model status, and health.
  • ML/DL Layer: Classical ML in `integration_real.py` and simulated DL; training/evaluation utilities under `explainability_utils/`.
  • Explainability: SHAP/LIME/Captum utilities in `explainability_utils/explainability.py`.
  • Infra: Multi-stage `Dockerfile` and `docker-compose.yml` orchestrate API, dashboard, and optional Redis/Postgres/Nginx.

Data Flow

  1. Input data (real or sample) is loaded in the dashboard and/or posted to API.
  2. Clinical scores and model predictions are computed (baseline + simulated DL + ensemble).
  3. Explainability and narratives are generated to justify risk.
  4. Results are shown in Streamlit and can be exported; API logs predictions to JSONL.

Third-Party Dependencies

PyTorch, scikit-learn, SHAP, LIME, Captum, Plotly, Streamlit, FastAPI, Uvicorn, NumPy, pandas, Matplotlib, Seaborn.

class SepsisExplainer:
    def get_shap_explanations(self, X: np.ndarray, max_evals: int = 100):
        shap_values = self.shap_explainer(X, max_evals=max_evals)
        feature_importance = np.abs(shap_values.values).mean(axis=0)
        return { 'shap_values': shap_values.values, 'feature_importance': pd.DataFrame({ 'feature': self.feature_names, 'importance': feature_importance }) }

13) Novelty & Societal Impact

What makes this project novel

  • End-to-end integration: Combines clinical scores, multiple ML/DL models, explainability, and a usable dashboard in one system.
  • Dynamic explainability: Time-evolving feature importance (explainability-over-time) to justify alerts longitudinally, not just at a single point.
  • Demo-to-deployment path: Clear Dockerized pathway from local demo to microservice-backed deployment.
  • Clinician-centered UX: Threshold tuning with live sensitivity/specificity plus narrative explanations to bridge AI and clinical reasoning.

Clinical and societal benefits

  • Earlier intervention: 4–6 hour lead-time can reduce complications, length of stay, and mortality.
  • Resource stewardship: Prioritizes high-risk cases for rapid evaluation in busy ICUs.
  • Education: Narratives and factor summaries support training for residents and nurses.
  • Equity focus: Built-in fairness view encourages subgroup performance review and bias monitoring.

Ethics, safety, and fairness

  • Transparency: SHAP/LIME/Captum outputs plus clinical narratives explain model behavior.
  • Human-in-the-loop: System provides recommendations, not orders; clinicians retain final judgment.
  • Bias awareness: Fairness tab surfaces subgroup differences; encourages local validation before adoption.
  • Privacy: Intended to run on secure hospital infrastructure; avoid exporting PHI; audit logs should be access-controlled.

Adoption and workflow integration

  • Stakeholders: Intensivists, nursing staff, quality/safety officers, IT, and administrators.
  • Workflow fit: Dashboard for bedside review; API for EHR integration and alerts.
  • Rollout: Start as a decision-support pilot with shadow-mode monitoring, then phased activation.

Regulatory & compliance (assumed)

  • Clinical validation: Prospective evaluation and IRB oversight before clinical use.
  • Standards: Logging, versioning, and change control to support auditability.
  • Security: Network isolation, least-privilege access, encrypted at-rest/transport.

Limitations & future work

  • Data shift: Models can drift across hospitals; recommend periodic re-calibration and monitoring.
  • Labeling nuances: Sepsis onset labeling varies; align with local protocols.
  • Real-time feeds: Add streaming ingestion and robust failure handling for production.
  • Broader fairness: Expand equity metrics and intervention outcome monitoring.
14) Performance & Ops Tuning

API (FastAPI/Uvicorn)

  • Workers: Use multiple workers on multi-core hosts
    uvicorn api_service:app --host 0.0.0.0 --port 8000 --workers 2
  • Log level: Control via LOG_LEVEL (info/debug/warn) for noise vs. visibility.
  • Thread pool: Prediction runs in a threadpool; increase max_workers in the executor if needed.

Dashboard (Streamlit)

  • Caching: Prefer @st.cache_data for expensive data loads.
  • Plotly: Reduce points, set use_container_width=True, avoid heavy redraws.
  • State: Store uploaded or manual patient data in st.session_state to avoid recomputation.

Explainability workloads

  • Background data: For SHAP/LIME, cap background samples (e.g., 100–500) and cache preprocessed arrays.
  • Batching: Run explanations asynchronously or off the request path; precompute for demo patients.

Docker & Compose

  • Resources: Allocate CPU/RAM limits appropriately; mount only needed volumes.
  • Build size: Keep base slim; avoid unnecessary COPY of large dirs/artifacts.
15) Professor Q&A
  • Q: How is the 4–6 hour lead-time measured?
    A: Using time-stamped labels and predicted probabilities, we compute the time gap between first threshold-crossing and sepsis onset (see explainability_utils/metrics.py for lead-time and timeliness).
  • Q: Why combine classical ML and DL?
    A: Baselines offer interpretability and speed; DL captures temporal/complex patterns. The ensemble improves robustness and averages uncertainty.
  • Q: How do you handle missing ICU data?
    A: Masks and imputation in loaders; clinical-rule fallbacks in dashboard; GRU-D architecture (conceptually) supports time decay for missingness.
  • Q: What prevents overfitting?
    A: Patient-wise splits, early stopping, LR scheduling, and calibration. The demo simulates predictions where trained artifacts are not included.
  • Q: How did you choose thresholds?
    A: Picked to meet a target specificity (e.g., 80%) on validation; clinicians can tune thresholds based on operational goals.
  • Q: How is fairness addressed?
    A: A fairness tab surfaces subgroup metrics (age, gender, etc.). We recommend site-specific analysis and threshold adjustments as needed.
  • Q: What’s the clinical workflow impact?
    A: Risk alerts with explanations inform early interventions. The system augments clinician judgment; not an autonomous diagnostic.
  • Q: What are deployment prerequisites?
    A: Container runtime, secure network, PHI governance, and EHR integration. Start in shadow mode; collect feedback; then graduate to alerts.
  • Q: What about data shift across hospitals?
    A: Monitor drift, recalibrate periodically, and retrain with local data if performance drops.
  • Q: What is the main novelty?
    A: End-to-end, clinician-centered integration with dynamic explainability and a clear path from demo to deployable microservice.
  • Q: Why are the model performance metrics (AUPRC ~0.13–0.14) relatively modest?
    A: With a 2.17% positive rate (severe class imbalance), AUPRC ~0.13–0.14 is modest but expected. The models show good calibration (Brier ~0.11), meaning probabilities are reliable. The bottleneck is discrimination (ranking/separation), not calibration. Improvement requires better data sampling, loss function tuning, feature engineering, and hyperparameter optimization. See the "Model Quality Assessment" section for detailed recommendations.
  • Q: Can it run without Dataset.csv?
    A: Yes. The dashboard falls back to realistic sample data. Real data unlocks richer views.
  • Q: Can I use API only?
    A: Build/run the production Docker target or start Uvicorn locally; interact via /docs.
  • Q: How do I change risk thresholds globally?
    A: Use the dashboard sliders for demo; in production, persist thresholds in config and read in both API and UI.
  • Q: How do I disable optional services?
    A: Comment out redis, postgres, nginx in docker-compose.yml.
  • Q: How do I calibrate thresholds for my hospital?
    A: Evaluate ROC/PR on local validation data; choose a threshold meeting desired specificity (e.g., 80%).

Person A: Data Preprocessing

Role: Responsible for data preprocessing, cleaning, feature engineering, and data quality assurance.

  1. Q: What was your approach to handling missing values in the ICU dataset?
    A: I implemented a comprehensive missing value handling strategy using SimpleImputer from scikit-learn. The imputer was fitted only on the training set (to prevent data leakage) using the mean strategy for numerical features. Missing values were imputed with the mean of each feature computed from the training data. The fitted imputer was saved to outputs/cache/imputer.joblib for consistency across train/val/test splits. This ensures that validation and test sets use the same imputation parameters as the training set, maintaining data integrity.
  2. Q: How did you handle feature scaling and normalization?
    A: I used StandardScaler from scikit-learn to standardize all numerical features. The scaler was fitted only on the training set, computing the mean and standard deviation for each feature. The fitted scaler was saved to outputs/cache/scaler.joblib and applied to validation and test sets using the same parameters. This ensures that all features are on the same scale (mean=0, std=1), which is crucial for deep learning models and prevents features with larger magnitudes from dominating the learning process.
  3. Q: What was your strategy for patient-level data splitting?
    A: I implemented patient-level splitting (70/15/15 train/val/test) to prevent temporal leakage. This ensures that all records from a single patient belong to only one split. The patient IDs were shuffled using a fixed random seed (42) for reproducibility, then split proportionally. The splits were cached to outputs/cache/patient_splits_seed{seed}.json to ensure consistency across multiple training runs. This approach prevents information leakage where a patient's future data might appear in the training set while their past data is in the validation set.
  4. Q: How did you create sequences for time-series modeling?
    A: I implemented a sliding window approach to create sequences from the time-series data. For each patient, I generated sequences of length sequence_length (48 hours) with a step size of step_size (1 hour) and a prediction horizon of prediction_horizon (6 hours). The sequences capture the last 24-48 hours of patient data before the prediction point. For GRU-D, I also computed delta_t (time since last observation) for each feature, which is essential for the decay mechanism in GRU-D. The sequences are created with proper masking to handle variable-length sequences and missing observations.
  5. Q: What features did you engineer or create for the models?
    A: I engineered several temporal and statistical features including:

Person C: Deep Learning Models

Role: Responsible for deep learning models (GRU-D, LSTM, CNN-LSTM, Transformer) and training pipeline.

  1. Q: What deep learning architectures did you implement and why?
    A: I implemented four deep learning architectures:
    • GRU-D: Gated Recurrent Unit with Decay mechanism that explicitly models missingness patterns and time decay, ideal for irregularly sampled ICU data
    • LSTM: Long Short-Term Memory network that captures long-term dependencies in time-series data
    • CNN-LSTM: Convolutional Neural Network followed by LSTM that extracts local patterns before temporal modeling
    • Transformer: Attention-based architecture that captures global dependencies and parallelizes training efficiently
    Each architecture has different strengths: GRU-D handles missingness, LSTM captures temporal patterns, CNN-LSTM combines pattern recognition with sequence modeling, and Transformer provides global attention. The ensemble of all four provides robustness and diversity.
  2. Q: How did you handle the class imbalance problem in training?
    A: I implemented several strategies to handle the 2.17% positive rate:
    • BCEWithLogitsLoss with pos_weight: Set pos_weight = num_neg / num_pos to automatically weight positive examples higher during training
    • Focal Loss: Alternative loss function (γ=2, α≈0.25) that focuses learning on hard examples and downweights easy negatives
    • Label Smoothing: Optional label smoothing (0.05) for Transformer to prevent overconfidence
    • Ensemble averaging: Trained 3 seeds per architecture and averaged predictions to reduce variance
    • Threshold optimization: Selected decision threshold to achieve Recall≈0.85 on validation set
    These strategies ensure that models learn to distinguish positive cases despite the severe imbalance.
  3. Q: What was your training strategy and hyperparameter configuration?
    A: I implemented a comprehensive training strategy:
    • Optimizer: AdamW with learning rate 1e-3, weight decay 1e-4
    • Learning rate schedule: Cosine annealing with warmup (3-5 epochs) or ReduceLROnPlateau on validation AUPRC
    • Batch size: 64-128 (optimized for memory and convergence)
    • Gradient clipping: 1.0 to prevent exploding gradients
    • Mixed precision: AMP (Automatic Mixed Precision) for CUDA devices to speed up training
    • Early stopping: Stopped training if validation AUPRC didn't improve for 8 epochs
    • Max epochs: 60 (typically converged in 20-35 epochs)
    All hyperparameters are saved in config.json for each model for reproducibility.
  4. Q: How did you implement GRU-D's decay mechanism for missing values?
    A: GRU-D implements a decay mechanism that models missingness patterns:
    • Feature decay: Missing features decay toward their mean value using exponential decay: x_imputed = m_t * x_t + (1 - m_t) * (decayed_gamma_x * x_mean)
    • Hidden state decay: Hidden states decay toward zero using: h_decayed = decayed_gamma_h * h_t
    • Delta_t computation: Time since last observation (delta_t) is computed for each feature and timestep
    • Decay rates: decay_gamma_x and decay_gamma_h are learned parameters that control decay speed
    This mechanism allows GRU-D to explicitly model how missing values and time gaps affect predictions, making it ideal for irregularly sampled ICU data.
  5. Q: What were the final model performance metrics?
    A: Final test set performance (calibrated, ensemble of 3 seeds):
    • GRU-D: AUPRC 0.1355, AUROC 0.4970, Brier 0.1114
    • LSTM: AUPRC 0.1353, AUROC 0.5430, Brier 0.1112
    • CNN-LSTM: AUPRC 0.1342, AUROC 0.5412, Brier 0.1111
    • Transformer: AUPRC 0.1423, AUROC 0.5382, Brier 0.1112
    Calibration is excellent (Brier ~0.11), but discrimination is modest (AUPRC ~0.13-0.14) due to the severe class imbalance (2.17% positive rate). The models show good calibration, meaning probabilities are reliable, but need improvement in discrimination (ranking/separation).
  6. Q: How did you implement probability calibration?
    A: I implemented two calibration methods:
    • Platt Scaling: Logistic regression on logits to map uncalibrated probabilities to calibrated probabilities
    • Temperature Scaling: Single-parameter scaling (temperature) that adjusts the softmax output to improve calibration
    Calibration was performed on the validation set, and calibration parameters were saved to calibrator.joblib for each model. The calibrated models show excellent Brier scores (~0.11), indicating that predicted probabilities match observed frequencies well.
  7. Q: How did you ensure reproducibility in your training pipeline?
    A: I implemented comprehensive reproducibility measures:
    • Fixed seeds: Set random seeds for PyTorch, NumPy, and Python's random module
    • Patient splits: Used pre-defined patient splits from Person A (saved to outputs/cache/patient_splits_seed{seed}.json)
    • Model artifacts: Saved state_dict, config.json, threshold_r85.json, and calibrator.joblib for each seed
    • Version logging: Logged package versions and training parameters
    • Reproducible command: python train_models.py --seed 42 --num_seeds 3 ... produces identical results
    All artifacts are saved to outputs/models/ for reproducibility and deployment.
  8. Q: What challenges did you face with MPS (Apple Silicon) compatibility?
    A: I encountered several MPS-specific challenges:
    • Float64 not supported: MPS doesn't support float64, so all tensors must be float32. Fixed by explicitly casting pos_weight, logits, and targets to float32.
    • Transformer padding mask: Nested tensor ops (aten::_nested_tensor_from_mask_left_aligned) are not implemented on MPS. Fixed by removing src_key_padding_mask and implementing manual masked pooling.
    • Mixed precision: AMP/GradScaler is only enabled for CUDA, not MPS. MPS uses standard FP32 training.
    • Boolean tensor operations: Fixed boolean subtraction errors in GRU-D by using float casting.
    All fixes are documented in the code and troubleshooting section (Section 2: "Quick Start Guide").
  9. Q: How did you implement ensembling across multiple seeds?
    A: I implemented ensemble averaging:
    • Multi-seed training: Trained each architecture with 3 different random seeds (42, 43, 44)
    • Probability averaging: Averaged raw probabilities from all 3 seeds for each architecture
    • Calibration: Applied calibration to ensemble probabilities
    • Threshold selection: Selected threshold on ensemble validation predictions to achieve Recall≈0.85
    • Final metrics: Computed ensemble metrics on validation and test sets
    This approach reduces variance and improves robustness compared to single-seed models. Ensemble results are saved to outputs/results/model_comparison.csv.
  10. Q: How are your deep learning models integrated into the production system?
    A: Deep learning models are integrated through:
    • Integration class: SepsisPredictionIntegration in integration_real.py loads trained models from outputs/models/
    • Model loading: Loads state_dict, config.json, threshold_r85.json, and calibrator.joblib for each seed
    • Ensemble prediction: Averages probabilities across seeds for each architecture
    • API endpoints: FastAPI service exposes predictions via POST /predict and POST /compare
    • Dashboard: Streamlit dashboard displays predictions in "Model Predictions" tab
    • Docker deployment: All models are containerized for production deployment
    The system seamlessly integrates all 4 architectures with baseline models for unified ensemble predictions.

Person D: Explainability and Dashboard

Role: Responsible for explainability (SHAP, LIME, Captum), interactive dashboard, and API integration.

  1. Q: What explainability methods did you implement and why?
    A: I implemented three explainability methods:
    • SHAP (SHapley Additive exPlanations): Game-theoretic approach that provides feature contributions satisfying desirable properties (efficiency, symmetry, dummy, additivity)
    • LIME (Local Interpretable Model-agnostic Explanations): Local linear approximation that explains individual predictions by training interpretable models on perturbed inputs
    • Captum: PyTorch-native explainability library that provides gradient-based, attention-based, and perturbation-based methods
    These methods provide different perspectives on model decisions: SHAP provides theoretically grounded feature importance, LIME provides local interpretability, and Captum provides model-specific explanations. The combination gives clinicians multiple ways to understand and trust model predictions.
  2. Q: How did you implement dynamic explainability (explainability-over-time)?
    A: I implemented get_dynamic_explainability() in explainability_utils/explainability.py:
    • Temporal feature importance: Computes feature importance for each timestep in a 24-48 hour window
    • Heatmap visualization: Creates time-series heatmap showing how feature importance evolves over time
    • Top features tracking: Identifies most important features at each timestep and tracks their evolution
    • Dashboard integration: Displays in the "Dynamic Explainability" tab with interactive Plotly charts
    This enables clinicians to understand how risk factors evolve longitudinally, not just at a single point in time, which is crucial for sepsis prediction where early warning signs may appear gradually.
  3. Q: What features does the Streamlit dashboard provide?
    A: The dashboard (dashboard_real.py) provides 9+ interactive tabs:
    • Risk Overview: Overall sepsis risk score, level, and actionable recommendations
    • Model Predictions: Individual model predictions with confidence intervals and ensemble average
    • Risk Trajectory: Time-series plot showing risk evolution over 24-48 hours
    • Explainability: SHAP/LIME/Captum feature importance plots and narrative explanations
    • Dynamic Explainability: Temporal feature importance heatmap showing evolution over time
    • Patient Data: View and edit patient data (vitals, labs, demographics)
    • Performance: Model performance metrics (ROC, PR curves, confusion matrices)
    • Clinical Workflow: Clinical scores (SIRS/qSOFA/SOFA) and recommendations
    • Fairness: Subgroup performance analysis (age, gender) for bias monitoring
    The dashboard provides a comprehensive interface for clinicians to interact with the sepsis prediction system.
  4. Q: How did you integrate the FastAPI backend with the Streamlit dashboard?
    A: I implemented a microservice architecture:
    • FastAPI backend: api_service.py provides RESTful API endpoints (POST /predict, POST /explain, POST /clinical-scores, etc.)
    • Streamlit dashboard: dashboard_real.py can call API endpoints or use local computation
    • Integration class: SepsisPredictionIntegration provides unified interface for both API and dashboard
    • Docker Compose: Orchestrates both services with proper networking and dependencies
    • Health checks: API health endpoint (GET /health) for monitoring
    This architecture allows the dashboard to be used standalone or connected to the API service, providing flexibility for different deployment scenarios.
  5. Q: How did you generate narrative explanations for clinicians?
    A: I implemented narrative generation in the explainability module:
    • Feature importance analysis: Identifies top contributing features from SHAP/LIME/Captum
    • Clinical interpretation: Maps feature names to clinical terms (e.g., "HR" → "Heart Rate", "MAP" → "Mean Arterial Pressure")
    • Risk level narrative: Generates sentences like "High risk due to elevated Lactate (2.5 mmol/L) and increased Heart Rate (110 bpm)"
    • Recommendations: Suggests actions like "Close monitoring recommended" or "Repeat laboratory tests in 2-4 hours"
    • Dashboard display: Shows narratives in the "Explainability" and "Risk Overview" tabs
    These narratives bridge the gap between technical model outputs and clinical reasoning, making AI predictions more accessible to clinicians.
  6. Q: What visualization libraries did you use and why?
    A: I used multiple visualization libraries for different purposes:
    • Plotly: Interactive charts for dashboard (risk trajectories, ROC/PR curves, feature importance) - provides zoom, pan, hover tooltips
    • Matplotlib: Static plots for training curves and performance metrics - lightweight and publication-ready
    • Seaborn: Statistical visualizations (confusion matrices, distribution plots) - built on Matplotlib with better defaults
    • SHAP: Built-in visualization for SHAP values (waterfall plots, summary plots, bar plots)
    Plotly provides interactivity for exploration, while Matplotlib/Seaborn provide static plots for documentation. The combination enables both interactive exploration and static reporting.
  7. Q: How did you implement the fairness analysis feature?
    A: I implemented fairness analysis in the "Fairness" tab:
    • Subgroup definition: Groups patients by age (e.g., <65, ≥65) and gender (Male, Female)
    • Performance metrics: Computes AUROC, AUPRC, Precision, Recall, F1 for each subgroup
    • Disparity detection: Identifies performance gaps between subgroups
    • Visualization: Bar charts and tables comparing subgroup performance
    • Bias monitoring: Encourages regular review to ensure equitable performance
    This feature helps identify potential biases in model predictions and ensures equitable performance across demographic groups, which is crucial for clinical AI systems.
  8. Q: How did you handle real-time predictions and performance optimization?
    A: I implemented several optimization strategies:

    • Background tasks: Logging and non-critical operations run as background tasks
    • Batch prediction: POST /predict/batch endpoint for efficient batch processing
    • Explainability optimization: Limited background samples for SHAP (100-500) and cached preprocessed arrays
    • Docker optimization: Multi-stage builds to reduce image size and startup time
    These optimizations ensure the system can handle real-time predictions efficiently while maintaining responsiveness.
